- **The header-encoding finding (A6).**
  - The website's usernames are ASCII only: seasonal-entertainment `shared/accountRules.js:14`.
  - It sends the name raw: `server/src/games/embeddedRoutes.js:53`.
  - Node carries header bytes as latin1. The kit decodes them as strict UTF-8, so umlauts and
    emoji sent as UTF-8 work. Malformed bytes give no identity, and since v0.9.1 so do control,
    line-separator and bidi characters.
  - If the website ever allows non-ASCII names, it must send them as UTF-8 bytes: Node's
    `setHeader` refuses characters above U+00FF.
- **The text the website's AUTH.md needs (A5),** at `e7b995c`, "Two-factor authentication
  (2FA)":
  1. In "Setup", replace "only their SHA-256 hashes are stored." with: "Only their HMAC-SHA-256
     is stored, keyed with `RECOVERY_CODE_KEY` (32 random bytes or more, as base64; its own key,
     never `SECRET_ENCRYPTION_KEY`), so a copy of the table cannot be searched for codes without
     the key. Codes stored before the change are plain SHA-256 hashes and still work: a code is
     looked up by both hashes, compared in constant time, and marked used in the same statement.
     Production refuses to start without the key or with the development key."
  2. In "TOTP secrets are encrypted at rest", replace "Recovery codes stay SHA-256 hashes and
     work whatever the key, so they remain the way back in." with: "Recovery codes do not depend
     on `SECRET_ENCRYPTION_KEY`: they are keyed with their own `RECOVERY_CODE_KEY`, so losing
     the encryption key leaves them the way back in. Losing `RECOVERY_CODE_KEY` voids the codes
     stored with it (the legacy SHA-256 ones keep working); those members make new codes after
     signing in. Keep both keys with the other secrets, not with the database backups."
